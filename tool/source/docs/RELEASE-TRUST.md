# Release trust root — who is allowed to say "this build is real"

## The problem this solves

The release gate refuses to mark a build release-eligible unless the evidence
(compile log, `ea.ex5`, tester report, stress matrix, deep review) is signed by
the machine that actually produced it.

A signature alone is not enough. In the `3.0.0a3` R2 build the verifier read the
signing **public key** from the `VCK_RUNNER_PUBLIC_KEY_B64` environment variable
and trusted whatever it found there. An audit demonstrated the consequence:

1. Generate a brand-new Ed25519 keypair.
2. Fabricate the evidence — including an `ea.ex5` that is literally the ASCII
   string `TOTALLY_FAKE_BINARY_...`.
3. Sign the canonical payload with the attacker's own private key.
4. Export the matching public key into the environment variable.

Result: `status: PASS`, `release_eligible=True`. The signature verified
flawlessly — against a key nobody had ever authorised. This is tracked as
**ADV-6 (self-signing bypass)**.

The lesson generalises: *a signature is only worth the provenance of the key
that made it.*

## The fix: pin the key in the repository

Every project now carries `RELEASE-TRUST.yaml`, generated by `vkmql-new contract`:

```yaml
schema_version: 1
policy:
  require_pinned_runner_key: true
runner_keys:
  - key_id: windows-runner-01
    algorithm: Ed25519
    public_key_sha256: "<64-char sha256 of the raw 32-byte public key>"
    owner: "ops@example.com"
    note: "MT5 build box; key generated on the runner, never exported"
```

Verification now requires **all** of:

| Condition | Failure mode if absent |
| --- | --- |
| `runner_attestation` block with an Ed25519 signature | `INCOMPLETE` |
| `key_id` declared in the attestation | `FAIL` |
| `RELEASE-TRUST.yaml` present | `INCOMPLETE` |
| `key_id` named in the pin list | `FAIL` — unpinned key |
| SHA-256 of the supplied public key equals the pinned fingerprint | `FAIL` — key swap |
| Signature verifies over the canonical payload | `FAIL` |

Matching on `key_id` alone would be insufficient: an attacker could reuse the
authorised identifier with their own key material. The fingerprint comparison is
what actually binds the identity to the key.

## What this does and does not buy you

**It does not make forgery impossible.** No repo-local checker can achieve that,
because whoever can write the repository can also edit the pin file. Anyone who
tells you otherwise is selling something.

**What it buys is detectability and blast radius:**

- `RELEASE-TRUST.yaml` is a top-level contract artifact. It is covered by the
  contract stage, by owner approval, and by the evidence hash chain. Editing it
  is a visible, reviewable, hash-breaking act — whereas setting an environment
  variable leaves no trace in the artifact at all.
- An unpinned key is now a hard `FAIL`: an active, reported rejection rather
  than a silent pass.
- Key rotation becomes an explicit, auditable change to a reviewed file.

**The irreducible root of trust remains operator key custody.** The private key
must live on the native Windows runner and nowhere else. If that key leaks, the
pin protects nothing. This is stated plainly because a governance kit that
overstates its own guarantees is worse than one with no guarantees at all.

## Operator workflow

On the native Windows runner, once:

```bash
mql5-runner-key generate --key-id windows-runner-01 --out ~/.vck/runner.key
```

Copy the printed `public_key_sha256` into `RELEASE-TRUST.yaml` and commit it.
The private key stays on the runner.

After each real MetaEditor + Strategy Tester run, on that same machine:

```bash
mql5-runner-key sign ./MyEA --key ~/.vck/runner.key --key-id windows-runner-01
```

`sign` refuses to proceed if the manifest hashes disagree with the bytes on
disk, so an operator cannot be tricked into signing a payload that describes
different artifacts than the ones actually produced.

On the verifying machine:

```bash
export VCK_RUNNER_PUBLIC_KEY_B64="<public_key_b64>"
vkmql-check all ./MyEA
```

## Rotating or revoking a key

Add the new key to `runner_keys` and remove the old entry. Removal is immediate
revocation: any evidence signed by the removed key now fails with an unpinned-key
error. Keep rotations in the decision ledger so the change has a recorded reason.

## Regression coverage

The attack and its fix are pinned by tests that ship with the kit:

- `tests/test_adversarial_release_gate.py::TestAdv6SelfSigning` — four attack
  variants plus a positive control.
- `mql5-selftest` invariant `runner_key_pinning` — reproduces ADV-6 in-process,
  so it runs even in the slim distribution.

The positive control matters as much as the attacks: without it, every test
above would be satisfied by a gate that simply always says no — a useless gate
rather than a secure one.
